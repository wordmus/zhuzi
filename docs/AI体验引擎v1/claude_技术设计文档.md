# 东周实验室之二 · AI体验引擎：设计与实施文档

*v0.1 · 2026-10-16 · 读者：coding agent · 依据青竹的设计稿与后续补充整理*

## 0. 如何使用本文档

你（coding agent）将按本文档分阶段实现一个原型。阅读规则：

- 标记【定】的是青竹已决定的设计，不得改动；标记【设】的是为了能动手而给出的默认假设，可以在实现中替换，但替换时要在 `DECISIONS.md` 记录原因。
- 本文档不规定「某个游戏」。你实现的是产生并运行「呈现」的引擎，首个呈现只是用来验证引擎的垂直切片。
- 遇到文档没有覆盖的设计问题，先查第 12 节「待确认事项」；若在其中，用默认假设继续并记录，不要停下来等待。

## 1. 产品定义与不变量

- 【定】这是一台只为一个人存在的机器。交付物不是某个游戏，而是一群为该用户设计呈现、并随用户体验越做越好的心智。
- 【定】机器里的一切都是「呈现」，每段呈现由一个会设想用户的心智设计。呈现可以是游戏、电影，或介于两者之间的东西。
- 【定】电影与游戏位于交互性的两端：电影不让观众处理自己的预期，游戏允许玩家以交互验证预期。游戏设计的是玩法集，不是单个玩法。因此引擎必须能表示「用户预期」，即需要心智模型。
- 【定】机器目前的感官只有：文件、用户操作、时间流逝。不要伪造其他感官。
- 【定】首发垂类为历史类 RPG（背景：东周）。玩法由心智数值驱动，而不是概念数值驱动。
- 【定】产品不约定用户是人；接口层不得写死「人类用户」假设。
- 【设】首版为单用户、本地运行。

## 2. 术语表

| 术语 | 定义 |
| --- | --- |
| 心智 Mind | 由众多行动单元（模块）层层搭建的高层决策单元；每个角色都有一个 |
| 模块 Module | 心智的底层单元，如感官、记忆、胃一类预定义实体，对某类刺激有天生倾向 |
| 痕迹 Trace | 多个模块在一段时间内的连续活动记录；记忆是痕迹 |
| 意识 Awareness | 对当前时间窗口内痕迹的记录，本身也是一条痕迹；下一段意识可读取之前的意识痕迹，因此看起来连续 |
| 世界 World | 设定 + 运行 |
| 呈现 Presentation | 导演对世界的理解，被做成用户可交互的作品 |
| 导师 Mentor | 最高心智，分配资源、理解用户、决定主题；一切呈现最终由它赋予设定 |
| 导演 Director | 设计世界与呈现的心智 |
| 演员 Actor | 活在世界里的心智 |
| 双世界 | 导演所在的世界，与导演设计出的呈现世界，两者相连（见第 8 节） |
| 翻译层 Translator | LLM 所处的位置（见第 4 节） |
| 档案 Archive | 机器的历史档案，事件溯源式日志 |
| 花园 Garden | 导师心智过程的持续空间化界面 |

## 3. 总体架构

```
用户 ──操作/文件/时间──▶ [信号采集] ──▶ 档案 Archive（事件溯源，唯一事实来源）
                              │
                              ▼
   导师 Mentor（导师钟）──分派主题/资源──▶ 导演 Director（呈现钟）
        ▲   │                                   │ 设计/调整
        │   └──▶ 花园 Garden（可视化）          ▼
        │                              世界 World（设定+运行）◀── 演员 Actor 们
        │                                   │
        └──── 用户体验信号 ◀── 呈现运行时 Presentation Runtime ◀┘

   翻译层 Translator（LLM）：人类含义 ⇄ 符号心智状态，位于各层边界
```

层级本质是快与慢的设计方法：导师慢且贴近人类时间，演员快且服务于呈现。

## 4. LLM 的位置：翻译层

- 【定】LLM 是在人与非人之间翻译意义的翻译器，且应更多关注高层信息。
- 【设（由上推论）】心智状态的更新由符号系统执行，LLM 不充当底层更新规则。LLM 做两个方向的翻译：
  - 人→符号：史料、用户的话、导演的意图 → 符号化的初始参数、概念、目标。
  - 符号→人：心智状态、档案、导演的设计过程 → 可读文本、传记、花园内容、素材提示词。
- 【设】所有 LLM 调用经统一适配器，支持记录/回放缓存，使测试可复现；翻译结果必须通过 schema 校验后才能写入心智状态。
- 【设】LLM 不直接读写底层模块参数，只通过翻译接口提交「提案」，由符号层校验并应用。

## 5. 时间模型

- 【定】导师层最接近人类的时间流逝；其他层为呈现而设计，不必遵循现实时间，如同电影。
- 【定】有些角色的时间与用户一致，有些不一致。
- 【设】实现为三种钟：
  - 用户钟 UserClock：墙上时间。
  - 导师钟 MentorClock：与用户钟同速（可配置缩放系数，默认 1.0），驱动花园的缓慢变化。
  - 呈现钟 PresentationClock：每个呈现独立，可压缩、跳跃、暂停，由导演定义它与用户钟的映射 `ClockMap`。
- 每条档案事件同时记录它所属的钟和各钟读数。

## 6. 数据模型（最小集）

【设】用 Python + pydantic 表示（或等价类型系统），全部可 JSON 序列化并带 `schema_version`。

```python
class Module:        # 心智底层单元
    id: str; kind: str            # sensor / memory / drive / ...
    tendencies: dict[str, float]  # 对刺激类别的天生倾向，因角色而异
    rate: float                   # 活动频率（低频/高频）
    intensity: float              # 刺激度

class Trace:         # 痕迹
    id: str; t: ClockStamp
    module_ids: list[str]; payload: SymbolExpr; links: list[str]

class Awareness:     # 意识：对窗口内痕迹的记录，自身也是痕迹
    window: tuple[ClockStamp, ClockStamp]; trace_ids: list[str]; prev: str | None

class Mind:
    id: str; modules: list[Module]; traces: list[Trace]
    concepts: dict[str, SymbolExpr]    # 高层概念（如兼爱）的压缩表示
    model_of_others: dict[str, SymbolExpr]

class World:        setting: SymbolExpr; runtime_state: dict; entities: list[str]
class Presentation: world_id: str; director_id: str; units: list[UnitRef]; clock_map: ClockMap
class ArchiveEvent: id: str; clock: ClockStamp; actor: str; kind: str; data: dict
```

要点：

- 【定】心智用数学化符号构建，不把认知逻辑写死在函数里。`SymbolExpr` 是可序列化的表达式树（数据），由解释器求值。
- 【设】记忆激活分数 = 线索匹配度 × 模块共现 × 强度 + 近因项；近因只是其中一项，不得退化为「按时间从新到旧」。
- 【设】对他人的认知 = 用观察者自己的心智结构，结合当前情景参数化后，对他人的建模。

## 7. 模块规格与验收

| 包 | 职责 | 验收标准 |
| --- | --- | --- |
| `archive` | 事件溯源日志；所有层的行动与心智过程写入此处，可重放 | 同一事件流重放得到完全相同的状态哈希 |
| `symbolic` | SymbolExpr 定义、解释器、校验 | 不含任何角色专属逻辑；新增倾向只改数据 |
| `mind` | 模块、痕迹、意识窗口、记忆激活、信息压缩 | 单测证明近因不是决定激活的唯一因素；意识链可回溯 |
| `translator` | LLM 适配器、双向翻译、提案校验、记录/回放 | 非法提案被拒并写入档案；离线回放模式下全部测试通过 |
| `world` | 设定+运行；实体；演员的行动循环 | 无导演、无界面的无头运行 N 个 tick，结果可复现 |
| `presentation` | 基本单元：交互控制器、剧情器、可组合技能；电影式镜头记录 | 同一世界既能以游戏形式、也能以镜头记录形式各出一份 |
| `director` | 双世界中的设计循环、能力扩充 | 导演可在多轮中新增能力并写出传记 |
| `mentor` | 分配资源、理解用户、定主题、生成双世界 | 能由参数与提示词模板生成一对双世界 |
| `signals` | 采集用户操作、文件、时间并归一为事件 | 事件格式与用户类型无关 |
| `garden` | 导师心智过程的持续空间化界面 | 变化只能增量发生（见 9.3） |
| `assets` | 文生图、视频、音频适配器与保留或丢弃的决策钩子 | 生成资产进入设定前必须经过心智的去留决定并记入档案 |

## 8. 双世界结构

- 【定】导师决定主题并交给导演；与其凭空造出导演，不如构造导演的环境。
- 【定】导演身处一个世界，在其中设计另一个世界；他带着私人经验和所在世界的公共知识，并在自己的世界里连接另一个世界。
- 【定】首次由青竹设计该结构；此后导师自己填参数和提示词来生成双世界。
- 【定】导演设计时的想象与思辨可以披露出来，成为传记。

【设】据此实现为模板 + 生成器：

```python
class DualWorldSpec:
    theme: str                      # 导师给出的主题
    outer_world: WorldSpec          # 导演所在世界（公共知识来源）
    director: MindSpec              # 含私人经验、自身目标、对体验的理解
    inner_world: WorldSpec          # 被设计的呈现世界
    link: LinkSpec                  # 导演如何接入内世界（观察 / 修改 / 镜头）
    biography_policy: BiographyPolicy  # 披露哪些设计思辨为传记
    slots: list[Slot]               # 导师可填写的参数与提示词位
```

agent 的任务：实现 `DualWorldSpec` 的 schema、校验与实例化，并提供一个用占位内容写成的示例实例。真实的结构设计由青竹提供，所以实现时要把「结构」与「slots 的取值」分离，使后者可以由导师程序化填写。

## 9. 关键机制

### 9.1 共同进化

- 【定】导演的行动能力被设计所限，所以要不断新增能力，直到达到目标体验；导演对自身能力的评估受导师和结构影响。
- 【设】实现为循环：设想用户体验 → 对照目标 → 提出缺失能力 → 新增（经翻译层生成单元）→ 重新设想。结束条件见第 12 节。

### 9.2 信息压缩

- 【定】高层概念需要角色对信息进行压缩，且高层对底层有倾向性关注。
- 【设】concepts 由翻译层从史料提出提案，符号层存为表达式。验收用例用「兼爱」：同一概念在不同角色的心智中应有不同的压缩结果。

### 9.3 花园

- 【定】导师的心智过程要有界面体现并进入档案；提供一个容许时间流逝的空间锚点以增强私人感与亲密感；初次由 LLM 设计，之后随用户的时间节奏改造，不得一次性剧变（如花园突然变成一艘船）。
- 【设】每次改造受「变更预算」限制：单次变更占整体元素的比例有上限，并按导师钟节流。

## 10. 实施路线

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| P0 | 仓库骨架、`archive`、`symbolic`、记录/回放测试框架 | 重放一致；CI 通过 |
| P1 | `mind`：模块、痕迹、意识、记忆激活 | 满足第 7 节 mind 验收 |
| P2 | `translator`：史料 → 初始参数（一位东周人物）；提案校验 | 离线回放下完整跑通 |
| P3 | `world` 无头运行 2 至 3 个演员 | 可复现；能从档案读出一段「他们经历了什么」 |
| P4 | `presentation`：一个可交互的小切片，用户操作进入 `signals` | 游戏端用户能用交互验证预期；电影端可导出镜头记录 |
| P5 | `director` + 双世界生成 | 导演新增至少一项能力并产出传记 |
| P6 | `mentor` + `garden` | 导师根据用户信号调整资源与主题；花园增量变化 |
| P7 | 共同进化回路与 `assets` | 跑通一轮自动的「设想—调整」闭环 |

每个阶段结束：更新 `DECISIONS.md`，列出新增或改动的【设】项。

## 11. 仓库结构与工程规则

```
engine/
  archive/ symbolic/ mind/ translator/ world/
  presentation/ director/ mentor/ signals/ garden/ assets/
  specs/            # 双世界模板、示例实例
tests/
DECISIONS.md        # 所有【设】的变更记录
```

- 【设】Python 3.11+、pydantic、SQLite 存档案，前端用 TypeScript 做呈现壳与花园；均可替换。
- 所有随机性使用显式 seed；所有 LLM 调用经适配器并可回放。
- 认知逻辑必须是数据（SymbolExpr），不得散落在函数里。
- 首版不做：3D、多用户、联网同步；但接口不得排除它们。

## 12. 待确认事项

| 问题 | 默认假设（继续实现时使用） |
| --- | --- |
| 用户信号的最小集合 | 操作序列、停留时长、选择与回退、显式评价 |
| 导演何时停止新增能力 | 导师设定的体验目标被导演自评满足，且至少有一次真实用户信号印证 |
| 历史人物参数如何验证 | 先以史料一致性（可追溯到出处）验收，再以玩家感受迭代 |
| 首个呈现用哪位人物与场景 | 青竹指定；默认任选一个含「兼爱」的东周场景做占位 |
| 技术栈与 LLM 供应商 | 见第 11 节；供应商经适配器，不绑定 |
| 双世界的真实结构 | 青竹提供；在此之前用占位示例 |
